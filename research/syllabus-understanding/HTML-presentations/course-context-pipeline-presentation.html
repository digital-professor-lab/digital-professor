Provider-agnostic by design

The LLM is any OpenAI-compatible endpoint; you swap provider/model/key via config, CLI, or .env — no code change. Default is local Ollama (free); we generate on DeepSeek (deepseek-chat) for quality.

Ollama (local)DeepSeekOpenAIOpenRouterJHU Gateway

Two generation strategies

single

One call for the whole file. Needs a large output budget (Claude Sonnet, gpt-4.1).

by_module

An outline call, then one call per module, then assemble. Keeps each response small so a modest cap (DeepSeek ~8K) never truncates.

Why per-module matters. A whole CourseContext can exceed a model's per-response limit and truncate into invalid JSON. The by_module strategy generates the outline first, fills each module in its own call (feeding earlier concept ids forward so prerequisites resolve), then de-duplicates sources and back-fills links on assembly.

3Validator & Review Flagger Phase 2

Two pure, deterministic tools between generation and publishing. The Validator is a gate; the Flagger is a to-do list for a human.

Validator — the gate (errors block)
Is the file well-formed? Any error → discard & regenerate (capped). Rules V-01–V-10:
  • top-level shape, required/unknown fields (V-01–V-02)
  • enums & formats; unique ids that follow the patterns (V-03–V-04)
  • every link resolves; forward/reverse links agree (V-05–V-06)
  • prerequisites acyclic, never a later module (V-07)
  • no empty / "TBD"; assumptions well-formed; provenance valid (V-08–V-10)
Review Flagger — the worklist (never blocks)
Which inferred content should a human check? Driven by the assumptions log:
  • only the high-stakes check-first fields: difficulty_notes, key_definitions, prerequisite_ids, assumed_background
  • skips inferences the model marks confidence: high
  • blanket (wildcard) assumptions as global notes

The rules, with a trigger example

Validator rules (V-*) are errors — any one blocks publication and regenerates the file. Flagger rules (F-*) never block; they add a review item.

RuleFires when…Example that triggers it
V-01top-level shape is wrongan unexpected top-level key (e.g. a typo Modules), or Course missing
V-02a required field is absent, or an unknown field appearsa Concept with no summary; a bonus color field
V-03an enum/format is invalidbloom_level: "memorize"; weeks: 2 (number, not "2")
V-04an id is duplicated or off-patterntwo concepts share an id; a LO id not ending .lo<n>
V-05a reference points to a missing recordprerequisite_ids → a concept that doesn't exist
V-06a forward link and its reverse disagreeConcept.module_id = M but M.concept_ids omits it
V-07a prerequisite is cyclic / in a later module / selfA requires B and B requires A
V-08a required value is empty or "TBD"summary: ""; a Module with concept_ids: []
V-09an assumptions entry is malformedmissing reason; confidence: "pretty-sure"
V-10provenance is missing or not the enumprovenance: "Syllabus 7.2" instead of ai_inferred
F-01a check-first field is inferred and not confidence: highan inferred difficulty_notes marked medium → review item
F-03a blanket (wildcard) assumption existsid: "calc1.*" on difficulty_notes → one global note

Check-first fields (what F-01 watches): difficulty_notes, key_definitions, prerequisite_ids, assumed_background. Warnings (W-01/W-02) are disabled in v1; the blanket F-02 rule was dropped.

Confidence-aware flagging

The generator now self-rates each assumption high / medium / low. The Flagger surfaces only the not-confident ones on high-stakes fields — so "flag every inferred value" (noise, since a syllabus-only file is almost all inferred) becomes "flag the shaky misconceptions and background." On a real DeepSeek run that cut the worklist roughly in half.

A real review worklist

Running the Flagger on our DeepSeek CourseContext produced calc1.deepseek-chat-v4.review.json: 29 items — 19 inferred difficulty_notes, 9 prerequisite_ids, and 1 assumed_background. An item appears when the generator logged an assumption on a check-first field that it did not mark confidence: high; high-confidence inferences were skipped. Two real items:

    },

      "priority": "check_first",

Each reason is the generator's own assumption + reason text, so the reviewer sees what was inferred and why. Nothing with confidence: high is listed — the Flagger assumes those are standard, correct inferences a human can skip.

Running it standalone (no generation, no model, no key)

The Validator and Flagger are independent of the builder — run them on any existing CourseContext file with --validate-only. (The Validator also powers the regenerate-on-error loop inside the builder.)

      --from-json specs/examples/calc1.course-context.json

4The QuestionSchema Builder Phase 3

The target for one question. Built from the CourseContext + the question, then frozen and handed to the Tutoring Engine read-only.

What's copied vs. written by the LLM

Copied verbatim from CourseContextWritten by the LLM (runtime)
learning_objectives, misconception description/mitigation, prerequisite names, source_ids reference_answer (solved & self-checked), correct_approach, alternative_approaches, each prerequisite relevance, each misconception cue

The runtime id is derived — <concept>.adhoc-<8 hex>, a SHA-1 of the normalized prompt — and built_from.content_sha256 pins the exact CourseContext bytes for reproducibility. Concept-match (which concept the question tests) is retrieval's job (Sean); until then the builder asks the LLM to pick from the concept list, or takes an explicit --concept-id.

Worked example: a student types $\int x\cos(x)\,dx$

It looks like substitution but needs integration by parts. With no --concept-id given, the builder's LLM concept-match picked integration by parts plus two related concepts (antiderivatives, product/quotient rules). It copied the objectives and the two CourseContext misconceptions, had DeepSeek solve and differentiate-check the answer, and added two runtime misconceptions. Deterministic where it counts. The runtime id is a SHA-1 of the normalized prompt, so it is reproducible — the same adhoc-d7df1b60 as the golden example — and built_from.content_sha256 pins the exact CourseContext bytes. The solution, approaches, cues, and extra misconceptions are DeepSeek's.

How we called it

$ python -m course_context_pipeline.build_question_schema \
      --course-context specs/examples/calc1.course-context.json \
      --question "\\int x\\cos(x) dx" \
      --base-url https://api.deepseek.com/v1 --model deepseek-chat \
      --api-key-env DEEPSEEK_API_KEY --out output/qs.xcosx.json

Pass --concept-id <id> to set the concept explicitly and skip the match call. Plain English works too (--question "integral of x cos(x)") — only the adhoc- id changes, since notation isn't canonicalized in v1.
