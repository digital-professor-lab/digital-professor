1The big picture

What the Course Context module is responsible for, and what it hands to the rest of the system.

Course Context is the structured, linked description of one course that the rest of the Digital Professor reads. It is produced once per course from course materials, reviewed by a human, and then consumed read-only. The module owns two outputs:

CourseContext — the knowledge base

  • Course → Module → Concept → objectives, sources, questions
  • The prerequisite graph between concepts
  • Difficulty notes (misconception → mitigation) per concept
  • Per-record provenance + a logged assumptions list

QuestionSchema — the per-question target

  • Everything a correct solution to one question requires
  • The valid approach(es), reference answer, prerequisites
  • The misconceptions the question tends to trigger
  • Built on demand, handed to the Tutoring Engine read-only
The core idea. The syllabus defines what is taught and in what order; the module turns that into a retrievable knowledge base, and for any question retrieves a concrete target. Tutoring then becomes "close the gap between the target and the student."

Documented across three files: course-context.md (the spec), course-context.validation-and-flagging.md (the tools), and course-context.example-calc1.md (the worked example).

3The Course Context schema

Six linked record types. Concept is the hub.

The chain Course → Module → Concept → LearningObjective / Source / AssessmentQuestion is a reading order, not the storage layout. Objectives, sources and questions all attach to a Concept; a question reaches its sources only through its concepts; prerequisites are Concept→Concept links (acyclic).

RecordKey fields
Courseid, title, level, duration_weeks, assumed_background, module_ids[]
Moduleid, course_id, title, goal, weeks, concept_ids[]
Conceptid, module_id, name, summary, key_definitions[], prerequisite_ids[], objective_ids[], difficulty_notes[{misconception, mitigation}], source_ids[], question_ids[]
LearningObjectiveid, concept_id, text, bloom_level
Sourceid, type, citation, section, text_chunk
AssessmentQuestionid, concept_ids[], objective_ids[], type, difficulty, prompt, solution, rubric, common_wrong_answers[], requires_figure

Records link by id, so the whole context around any item is one lookup plus a few link-follows — exactly what the builder needs to assemble a target on demand. A small additive field, provenance, rides on every record (schema 1.1).

4Provenance — where the trust comes from

A syllabus-only file is a skeleton with plausible content on it. Provenance makes the difference explicit.

source_backed

Every non-structural value on the record is stated in, or mechanically copied from, the supplied material.

ai_inferred

At least one value was generated by the model beyond what the material states.

Weakest-link rule. A record's provenance is the weakest of its non-structural fields. In a syllabus-only file, structure, order and citations are source-backed; summaries, definitions, objectives, prerequisites, difficulty notes, questions and solutions are not.

So what carries the trust? The provenance field, the assumptions log (one entry per inference — what was inferred, on which field, and why), and the human review checklist. The model never leaves a field blank or "TBD" — it infers a value and logs the inference.

Validator — the gate
Is the file well-formed? A file with any error is regenerated, not hand-patched. Checks include:
  • structure, required fields, enums (V-01–V-03)
  • unique IDs that follow the patterns (V-04)
  • every link resolves; forward/reverse links agree (V-05–V-06)
  • prerequisites acyclic, never point to a later module (V-07)
  • no null / empty / "TBD"; assumptions resolve (V-09–V-11)
Review Flagger — the worklist
Which content should a human look at? It does not block; it produces a report:
  • every record named by an assumptions entry
  • the "check first" fields on AI-inferred records: solutions, rubrics, prerequisites, difficulty notes, assumed background
  • wildcard (blanket) assumptions as global notes

6The Question Schema

The target for one question: what a fully correct solution requires. Built from Course Context + the specific question, then frozen and handed to the Tutoring Engine.

FieldMeaning
concept_ids, learning_objectiveswhich concept(s) the question tests, and their objectives (copied verbatim)
prerequisite_conceptsthe direct prerequisites a student must already be able to use
correct_approach + alternative_approachesthe canonical technique (+ justification), plus other valid ones
reference_answerthe full worked answer — access-restricted, never shown to the student
common_misconceptionsmisconceptions to watch for, each with an observable cue
source_referencewhere the question is grounded in the course material
provenance, built_fromtrust level + the exact Course Context (SHA-256) used, for replay

The schema is not hand-written — every field is a lookup or a machine-checked build against the knowledge base. A bank question copies its fields; a runtime (student-typed) question gets an ad-hoc id and the builder writes & checks the solution (e.g. for an integral, by differentiating it back).

7Material lifecycle & the ingestion layer

Course materials play two roles, and enter at two different stages.

RoleMaterialsStageProduces
Structural inputsyllabus / course breakdownA — structure build V1the Course Context skeleton + Source references
Content inputlecture notes, textbook, slidesB — content ingestion post-V1normalized pages + stable line maps + versioned chunks
Key point. Building the course structure only needs the syllabus. Lecture notes and textbooks are not needed for that — they enter later, at an ingestion layer that fills in the real material behind the Source references so Sean's retrieval can ground on it.

The ingestion layer (Stage B)

  • Input: the Course Context (to link content to the right Concept/Source) + raw approved documents + ingestion config.
  • Output (handoff to retrieval): per document version — normalized page text, stable page/line mappings under a content_version, and versioned chunks linked back to Source/Concept (proposed as the IngestedSource record).
Normalized pages & stable line mappings. Each page is parsed into one clean, canonical text (consistent whitespace, headers/footers stripped, hyphenation rejoined) and its lines are numbered, so a citation (document, version, page, line_start–line_end) always resolves to the same passage and a highlight link can open and highlight it — even after the document is re-ingested. Think "line numbers pinned to a commit."

A Question Schema for a student's question

A student types $\int x\cos(x)\,dx$. It's not in the bank, so the builder runs the runtime path: match the concept (integration by parts), copy objectives & misconceptions, write and differentiate-check the answer.

{
  "question_id": "calc1.06-integral-applications.by-parts.adhoc-d7df1b60",
  "origin": "runtime",
  "concept_ids": ["calc1.06-integral-applications.by-parts"],
  "prompt": "\\int x\\cos(x) dx",
  "correct_approach": {
    "technique": "Integration by parts with u = x and dv = cos(x) dx",
    "justification": "x and cos(x) have no derivative relationship, so the
       substitution test fails; u = x simplifies under differentiation (LIATE)."
  },
  "reference_answer": "x sin(x) + cos(x) + C.  Check: d/dx[...] = x cos(x). ",
  "common_misconceptions": [
    { "description": "Choosing u, dv so the new integral is harder.",
      "cue": "Sets u = cos(x), dv = x dx; the new integral gets worse." },
    { "description": "Reaching for u-substitution because an x sits next to a
        trig factor, without the derivative-relationship check.",
      "cue": "Tried u = cos(x) or u = x^2 and it did not simplify." }
  ],
  "prerequisite_concepts": ["substitution", "product-quotient"],
  "provenance": "ai_inferred",
  "built_from": { "course_context_schema_version": "1.1", "content_sha256": "617281d1…" }
}

What the target drives in a session

Handed to the Tutoring Engine, this one record is enough to run a Socratic session: compare the student's approach to correct_approach, probe the prerequisite_concepts, and watch for each misconception's cue. The worked example traces a 13-turn session on this exact integral — a problem that looks like substitution but needs integration by parts.
